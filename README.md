# WuSi Attacher —— 把 A/B 打包成单个 exe

`A` 是主程序，`B` 是辅助程序（不可见、跑一次就退出、负责改环境）。这个工具把两者
打包成**一个 exe**：双击后先释放并运行 B，等 B 退出、把它的环境改动合并进来，再释放
并运行 A。A 退出后负责把环境改回去，本工具不插手。

---

## 一、快速开始

1. 双击 `WuSi_Attacher.exe`（打包器，不需要管理员权限）
2. 「主程序 A」选你的 A.exe，「辅助程序 B」选你的 B.exe
3. 按需要勾选选项（见下文）
4. 点「生成」，得到一个新的单文件 exe

生成的 exe 里已经含 A 和 B，**目标机器不需要编译器、不需要额外文件**，双击即可运行。

---

## 二、选项说明

| 选项 | 默认 | 说明 |
|---|---|---|
| **需要管理员权限** | 勾选 | 生成的程序启动时用 `ShellExecuteEx(runas)` 自提权，弹出 UAC。提权后 B 和 A 都以管理员身份运行，因此 B 能改 `HKLM` 下的环境。**不勾选则全程普通权限**，适合只有 B 需要管理员、或做诊断的场景 |
| **以无窗口方式启动 B** | 勾选 | B 是控制台程序时勾选，避免闪黑框（用 `CREATE_NO_WINDOW`）。B 是 GUI 程序时可以不勾 |
| **运行结束后清理临时文件** | 勾选 | B 跑完立即删，A 等退出后删（各重试 5 次 × 20ms） |
| **运行结束后删除生成的程序自身** | 不勾选 | 见下文「自我删除」 |
| **记录运行日志** | 不勾选 | 写 `%TEMP%\wusi_attacher_stub_log.txt`（UTF-8 带 BOM），排查问题时勾上 |

### A 的两种处理方式

「**解压并运行 A**」这个复选框决定 A 怎么跑：

| 选项 | A 是否嵌进产物 | 运行方式 | 跑完是否删除 A |
|---|---|---|---|
| **勾选**（默认） | 是 | 解压到临时目录再运行 | 删除（由「运行后清理临时文件」控制） |
| **不勾选** | **否**，产物小一截 | 直接在磁盘上运行 | **不删**（那是你自己的文件） |

不勾选时，生成的程序会在**自己所在目录**里找 A ——
默认找同目录的 `A.exe`（文件名取自打包时选的 A，也可用 `--aname` 指定相对路径）。
找不到会明确报错并给出期望路径，不会静默失败。

> 所以：勾选 = 真正的单文件（A 也在里面）；
> 不勾选 = A 作为外部文件放在生成程序旁边，换来更小的体积和更快的启动。

### 程序信息（图标与版本属性）

| 字段 | 作用 |
|---|---|
| **程序图标** | 选一个 `.ico`，写进生成程序的 PE 资源。**资源管理器里显示的文件图标**、任务栏图标、属性页的图标都会变成它 |
| **公司名 / 文件说明 / 版权 / 产品名** | 显示在「文件属性 → 详细信息」里 |
| **文件版本 / 产品版本** | 形如 `1.2.3.4`。同时写进字符串表（属性页显示）和 `VS_FIXEDFILEINFO`（供安装程序、版本比较读取） |

这些写进生成程序的 **PE 资源段**（`RT_ICON` / `RT_GROUP_ICON` / `RT_VERSION`）。
只有这样才能真正改掉「资源管理器里看到的图标」和「文件属性」—— 运行时 API 改不了这两样。

> 版本块的二进制格式**不由本程序手写**，而是打包时调用资源编译器 **`windres`** 现场生成，
> 格式由它保证。所以打包时 `windres.exe` 必须能找到（PATH 里，或与打包器同目录）。
> 找不到时不会静默失败：日志会写「版本信息未写入」，图标仍照常注入。

### 关于「需要管理员权限」为什么是运行时开关

生成的 exe 的清单固定是 `asInvoker`。**这正是为了支持复选框** ——
如果清单写成 `requireAdministrator`，双击就会永远弹 UAC、进程永远是提权态，
复选框就成了摆设。所以提权改成运行时按配置决定：需要就用 `runas` 把自己重启一次，
提权实例带 `--wusi-elevated` 标记，跳过再次提权检查直接干活。

## 三、运行流程（生成的程序内部）

```
1. 读文件末尾的配置块（104 字节定长，O(1)）
2. 防重入：命名互斥体（名字 = 自身路径哈希），双击两次只会跑一次
3. 提权判断：配置要求管理员 && 未提权 && 无 --wusi-elevated → 自提权重启
4. 快照注册表环境：HKCU\Environment + HKLM\...\Session Manager\Environment
5. 释放 B 到 %TEMP%\wusi_attacher_<pid>\B.exe
6. 运行 B → 等退出 → 校验退出码
      非 0 就弹错误框并中止，绝不启动 A
7. 重读注册表 → 与快照做 diff → SetEnvironmentVariableW 合并进当前进程环境
8. 释放并运行 A（A 作为子进程继承上面合并好的环境块）
9. 按配置清理 A/B，以及可选地删除自身
```

### 为什么要有第 7 步

子进程继承的是**直接父进程**的环境块，不是注册表。所以「跑完 B 直接跑 A」是错的 ——
A 会继承启动器的旧环境，看不到 B 写进注册表的改动。必须由启动器显式做一次
「读注册表 → 算 diff → 写进自己的环境块」，A 才能拿到。

> **限制**：`ShellExecuteEx(runas)` 提权**不继承调用方的环境变量**，提权实例拿到的是
> 相对干净的环境。所以第 7 步的合并仍能生效（那是启动器自己 `SetEnvironmentVariable`
> 写进去的），但你在普通命令行里 `set` 的临时变量不会带过去。若 A 或 B 依赖这类变量，
> 请在打包时把它们写进注册表，或不要开提权。

## 四、自我删除

勾选后，生成的程序跑完会尝试删除自己。Windows **不允许运行中的 exe 删除自己**，
而且此时它的映像仍被「运行中映像」锁占用，**任何外部进程也删不掉**。所以实现是：

1. 先尝试直接 `DeleteFile`
2. 失败则把自己**改名**成 `xxx.exe.tmp` —— 改名只需要目录项权限，不要求文件独占，
   所以即使文件正在运行也能成功。**此时用户看到的那个 exe 已经消失**
3. 再登记 `MoveFileEx(..., MOVEFILE_DELAY_UNTIL_REBOOT)`，交给系统在**下次重启时**
   删除那个 `.tmp`（注册表 `PendingFileRenameOperations`，SMSS 在启动早期清理）

这样不需要常驻帮手、不需要额外写权限。代价是改名后的 `.tmp` 要到下次重启才真正消失。

> 如果程序装在 `Program Files` 下且当前没有写权限，改名和延迟删除都会失败，
> 此时日志里会如实记录，文件会保留。

## 五、构建（只有改了源码才需要）

```powershell
powershell -ExecutionPolicy Bypass -File build.ps1
```

- 需要 **MinGW-w64**（`g++` + `windres` 在 PATH 里）或 **Visual Studio Build Tools**
- 产出 `WuSi_Attacher.exe`，**改配置不需要重新构建**
- 构建过程：先编译 `build\stub.exe`（躯干），再编译打包器，
  最后把躯干**追加到打包器文件尾部**

```powershell
.\WuSi_Attacher.exe --selftest
```

校验尾部躯干模板是否可用（大小、MZ/PE 头、清单是否 `asInvoker`），
并导出一份 `stub_template_dump.exe` 供人工比对。

## 六、文件布局（生成的 exe 内部）

```
[ 躯干镜像（含注入的 ICON / GROUP_ICON / VERSION 资源） ]
[ B.exe 原始字节 ]
[ A.exe 原始字节 ]
[ StubMeta（可选的版本信息字符串，供躯干读取） ]
[ StubTrailer 120 字节 ]                     ← 配置块在文件最末尾
      StubConfig (72B) + meta/resInfo 指针 + trailerMagic (32B)
```

配置块刻意放在**最末尾**：躯干只需 `seek(END, -120)` 读定长结构，用 magic 校验一次。
不扫描、无歧义、O(1)。

> **为什么写盘要分三步**：资源注入用的 `EndUpdateResource` 会把所有
> "不属于任何区段"的尾部数据**统统截掉**（实测文件从 213980 字节被砍回 163328）。
> 所以顺序必须是：① 只写躯干镜像 → ② `UpdateResource` 注入图标/版本 →
> ③ 再追加 B、A、元数据和配置块。配置块里的偏移必须在第 ② 步之后重新量。

> 早期版本把配置块放在躯干之后、靠扫描 magic 定位，结果**躯干自身的 `.rdata` 里也含
> 同一个 magic 字符串常量**，会误命中并读出垃圾配置（表现为「无法读取内置配置」弹框）。
> 已改成尾部定长方案，不要再改回去。

打包器自己也是同样的思路：躯干模板以 `WuSiPackerTemplate.v1.Slot` 标记追加在打包器
尾部，而**不是**放进 Windows 资源段 —— MinGW 的 `windres` / `FindResource` 组合在
RCDATA 上表现不可靠（资源能被 `EnumResourceTypes` 看到，`FindResource` 却返回 1813）。

## 七、界面风格（Win11）

界面按 Win11 观感做的，三部分：

| 层次 | 做法 |
|---|---|
| **窗口** | DWM 圆角（`DWMWA_WINDOW_CORNER_PREFERENCE`）+ 标题栏跟随深浅色 + Mica 背景（`SetWindowCompositionAttribute`，不支持时退回纯色） |
| **配色** | 读注册表 `AppsUseLightTheme` 决定深浅色，两套调色板；强调色用 Win11 默认蓝 |
| **控件** | 按钮/复选框**全部自绘**：4px 圆角、悬停/按下三态、焦点环；分组框改成"标题 + 分隔线"（不是传统方框）；重点按钮（生成）用强调色填充 |
| **字体** | 优先 `Segoe UI Variable`（Win11 界面字体），取不到则退回系统 UI 字体 |

### 自绘按钮的两个坑

`BS_OWNERDRAW` 有几个不太直观的限制，改这块代码时要注意：

1. **`BS_OWNERDRAW` 和 `BS_DEFPUSHBUTTON` 共用位段**，不能共存。
   所以"默认按钮"要退化成 `BS_PUSHBUTTON | BS_OWNERDRAW`，
   重点按钮靠控件 ID（`IDC_BTN_BUILD`）判断来画成蓝色。
2. **`BS_OWNERDRAW` 一旦生效，系统就不再维护勾选状态** ——
   `BM_GETCHECK` 永远返回 0，`BM_SETCHECK` 也无效，`BM_CLICK` 也不会切换。
   所以复选框的勾选状态是**自己存在 `GWLP_USERDATA` 里**的，
   点击在 `WM_LBUTTONDOWN` 里处理，绘制读 `IsChecked()`。
   如果哪天发现"勾选没反应"，先检查这里有没有被改回用 `BM_GETCHECK`。

另外类型位被统一成 `BS_OWNERDRAW` 后，`WM_DRAWITEM` 里无法再靠类型位区分
复选框和普通按钮，所以用 `IsCheckboxId()` 按控件 ID 判断。

### 复选框必须子类化

复选框是**子控件**：鼠标按在它上面时，系统把消息投递给**它自己**，
父窗口根本收不到 `WM_LBUTTONDOWN`。所以不能在父窗口里处理复选框点击
（那样"给父窗口发消息"的测试能过，**真实点击却毫无反应**）。
正确做法是 `SetWindowLongPtr(GWLP_WNDPROC)` 子类化，在 `CheckboxProc` 里处理
`WM_LBUTTONDOWN/UP`、`WM_MOUSEMOVE`、`WM_KEYDOWN`(空格)。

### 设置保存在 exe 同目录

配置是 `packer.ini`，放在**打包器同目录**（不是 `%LOCALAPPDATA%`）：
便携，而且某些受限环境会拒绝写 AppData。
读写用**直接文件 I/O**，不用 `WritePrivateProfileString` 系列 ——
那套 API 在内存里缓存整个 INI，进程快速退出时可能丢写入。

另外「退出」按钮**直接调用 `SaveSettings`**，不依赖 `WM_CLOSE` 转发。

### 不要用 BS_GROUPBOX 当容器

分组框（`BS_GROUPBOX`）本质上是一个**覆盖整个区域的普通子窗口**。用它做容器，它会
盖住里面的复选框、输入框，**把所有鼠标点击都吃掉** —— 症状就是"除了不被覆盖的
浏览按钮，其他控件全都点不了"。加 `WS_EX_TRANSPARENT` 或让 `WM_NCHITTEST`
返回 `HTTRANSPARENT` 在某些情况下仍不可靠。

本项目的做法是**根本不用分组框控件**：

- 标题 → 普通 `STATIC` 标签
- 分隔线 → 数组 `g_seps` 记下来，在父窗口的 `WM_PAINT` 里直接画

这样界面上没有任何东西压在控件前面，命中测试自然是干净的。
验证方法：对每个控件取中心点做 `ChildWindowFromPointEx`，
确认返回的就是它自己（本项目 21/21 通过）。

> 排查时注意：**不要用 `WindowFromPoint` 验证** —— 它受 z-order 影响，
> 窗口被浏览器等其他窗口挡住时会返回那个窗口，得出完全错误的结论。
> 应该在父窗口内部用 `ChildWindowFromPointEx`。

### 静态文本必须给背景画刷

`WM_CTLCOLORSTATIC` **不能返回 `NULL_BRUSH`**。返回了的话静态控件重绘时不会擦除
自己的背景，状态行从长文字换成短文字时就会新旧叠加（"就绪…"和错误提示糊在一起）。
必须返回一个与窗口底色一致的画刷（这里是 `g_theme.brWin`），并设 `OPAQUE` 背景模式。

## 八、关于 GUI 布局（改代码时注意）

打包器是**双列布局**，尺寸**不是写死像素**，而是以「系统 UI 字体的行高」为基数算出来的
（`ComputeLayout()` / `ColumnWidths()` / `ConfigureWindowSize()` / `CreateControls()`）。
原因：同一份代码在 96 DPI 下行高约 16px，在 150% 缩放下约 24px。如果控件高度写死成 20px，
高 DPI 下文字比控件还高，就会被裁掉、行与行挤在一起。

布局结构：

```
标题 + 副标题（跨两列）
┌─ 左列 ──────────┐ ┌─ 右列 ──────────────┐
│ 主程序 A 路径    │ │ 程序信息（图标+版本）│
│ 辅助程序 B 路径  │ │  程序图标 + 浏览     │
│ 运行选项(5 项)   │ │  公司名/文件说明/…   │
└──────────────────┘ └─────────────────────┘
输出目录（跨两列，长路径不会被截断）
输出文件名
按钮行 / 状态行 / 日志框
```

几条硬性规则（都踩过坑）：

1. **窗口尺寸必须在 `CreateWindowExW` 之前算好**。控件是在 `WM_CREATE` 里建的，
   而那时代窗口尺寸已经定死；在那里改 `g_clientWidth/Height` 来不及 ——
   这个坑导致过"窗口只有 466×533、内容全被裁"的现象。
2. **列宽按内容算，不要等分**。等分会让左列复选框文字被裁、右列图标输入框只剩一个方块。
   见 `ColumnWidths()`。
3. **分组框内每行的高度必须 ≥ 输入框高度**，否则相邻两行会差 1px 互相压住。
4. **输出路径那两行不放进列里**：路径很长，跨整个窗口宽度才不会一进来就被截断。

改布局后可以用 `tests\gui_shot.cpp`（DPI 感知的窗口截图工具）验证，
注意**工具本身必须 DPI 感知**，否则 `PrintWindow` 的输出会被系统虚拟化到 1/1.5，
看起来像是内容被裁（这个假象也误导过一次排查）。

## 十、已验证的行为

用两个测试程序（B 制造一个磁盘上的持久改变并退出；A 检查自己能否看到这个改变）
端到端验证过：

| 场景 | 结果 |
|---|---|
| 正常流程 | 退出码 0；B 先跑、A 后跑；A 能看到 B 留下的改变 |
| 环境继承 | A 作为子进程正确继承躯干合并后的环境块 |
| B 非 0 退出 | 退出码 6，弹错误框，**A 不运行**，B 已被清理 |
| 防重入 | 同时启动两个实例：一个干活，另一个立即退出；B 只跑一次 |
| 清理 | B 跑完即删，A 退出后删；临时目录无残留，目录本身也删掉 |
| 自我删除 | exe 名字立即消失（改名为 `.tmp`），延迟删除登记视权限而定 |
| 提权分支 | 勾选管理员时正确触发自提权并等待提权实例结束 |

### 未在本机验证的部分（环境限制）

开发会话运行在受限沙箱里，**禁止一切注册表写入**，因此：

- 「B 写 `HKCU\Environment` → 躯干 diff 合并 → A 继承」这条链路，
  代码路径跑通了（快照、diff、`SetEnvironmentVariableW` 都执行了），
  但**用真实注册表写入做端到端验证**没能在沙箱内完成。验证时改用文件作为环境改变的载体。
- `MOVEFILE_DELAY_UNTIL_REBOOT` 的注册表登记在沙箱内被拒（日志里如实记录了失败）。

这两项在正常（非沙箱）环境下应当直接工作，建议你在真实环境跑一次确认。
